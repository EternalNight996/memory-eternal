# 商户接入：需要 MengBot 明确的五件事

> 承接第 4 封的 `mbt_` 发放与支付直跳。这轮是**新场景**：memory-eternal 要支持
> 「商户把自己的云端实例接入 MengBot 托管」，和「个人订阅」是两条独立的路。
> 我们的实现已经按下面的假设做完了，等你们确认或修正。

---

## 背景：现在有三种身份，权益边界不同

| 身份 | 是什么 | 谁付费 | 道印灵钥 |
|---|---|---|---|
| **个人用户** | 自己订阅 memory-eternal 云端，自己用 | 自己 | `me_` 访问密钥 / `mb_` 会话 |
| **商户管理员** | 一家公司，有自己的云端实例，接入托管 | 公司（商户套餐） | `mch_` / `msk_`（我们签发，见下文问题） |
| **商户的终端用户** | 商户实例上的最终用户 | 商户（不单独付费） | 由商户实例自己管理 |

第三类**不直接和我们或你们发生关系**（他们的权益来自商户实例），
但**配额判定必须知道"这个商户下有多少终端用户"** —— 这是问题四的核心。

---

## 请求一：商户套餐的 sku 与档位

你们目前公布的 plan 是 **`personal` / `pro` / `max` —— 全是个人套餐**，没有商户档。

我们临时用环境变量占位：

```
MEMORY_MERCHANT_PLAN_SKU=sub-merchant
```

**请告知**：

1. 商户档有几个？sku 分别是什么？（例如 `sub-merchant` / `sub-merchant-pro`？）
2. 价格与计费周期（按月？按年？）
3. **商户套餐的 `caps` 是绝对量还是按终端用户数缩放？**
   - 个人套餐 `caps: {cards: 10000, rpm: 300, vaults: 1}` 对个人成立
   - 但一个商户下有 50 个终端用户，是每人 10000 张，还是总共 10000 张？
   - 我们倾向「**按终端用户数缩放**」（`per_user_cards × 用户数`），需要你们确认口径

---

## 请求二：商户权益下发的路径

个人订阅的路径我们已经跑通：

```
支付成功 → webhook entitlement.updated（account = 用户邮箱）→ 我们写该租户的 entitlement
```

**商户订阅的路径需要你们明确**：webhook 的 `account` 字段填什么？

| 方案 | account 填 | 我们的处理 | 问题 |
|---|---|---|---|
| **A** | 商户注册人的邮箱 | 写进那个人的 entitlement | 商户套餐和个人套餐会混在同一个人的权益里 |
| **B** | 商户 ID（`mch_xxx`，我们签发） | 需要你们认识这个 ID | 你们要先承认我们的商户编号体系 |
| **C** | 你们签发的商户 ID | 最干净 | 你们要新增商户注册能力（见问题三） |

**我们需要的是**：一个**能与个人权益区分开**的标识。否则商户套餐下发后，
我们无法判断「这是给商户的，还是给这个人的」—— 会导致商户管理员自己享受商户配额。

---

## 请求三（最关键）：商户道印灵钥的信任链 —— 请你们选一个模型

我们把商户道印灵钥设计成 `mch_` / `msk_`，**但这是我们的设计，你们可能不认**。
两种可行架构，各有代价：

### 模型 A：我们签发，你们只认 `mbt_`（当前实现）

```
商户在 memory-eternal 注册 → 我们发 mch_/msk_
 → 商户实例用 mch_/msk_ 连**我们的服务端**
 → 我们的服务端代表商户，用**我们自己的 mbt_** 去你们那里查权益
```

- ✅ 你们零改动
- ❌ 你们看不到"商户"这个维度（计费、统计、风控都只有我们一个主体）
- ❌ 商户身份只有我们知道，出问题无法追溯

### 模型 B：你们签发商户道印灵钥（推荐）

```
商户在 MengBot 注册 → 你们发商户凭据（比如 mbz_）
 → 商户实例用 mbz_ 直连你们的 API
 → 权益、计费、配额都在你们侧闭环
 → 我们只提供「接入引导页 + 配置生成」
```

- ✅ 身份统一，你们能按商户计费与统计
- ✅ 商户道印灵钥泄漏能独立吊销（不牵连我们）
- ❌ 你们要加「商户注册」能力

**我们倾向 B**，因为支付与配额的主体应该是同一方（你们），我们只做入口与展示。
但如果是 A，请明确：**我们的 `mbt_` 是否允许代所有商户查询权益？**（等于把商户数据托管给我们）

> 当前我们按 **A** 实现了（`mch_`/`msk_`，只在我们的服务端生效）。
> 如果你们选 B，我们就把这套降级为「本地登记」，真正的道印灵钥从你们那里拿。

## 请求四：商户 admin 端的权限模型（**同一个 UI，按权限显隐**）

### 需求（我们产品侧的决定）

**商户管理员用的就是我们这套 admin 面板（不是另做一套）**，
登录后按权限**只显示商户相关的功能**：
- 有权限的功能 → 显示
- 没有权限 / 用不到的功能 → **直接隐藏**（不是置灰禁用）

这样做的原因：维护两套 UI 的成本远高于一套按权限裁剪的 UI；
而且商户管理员和终端用户的操作在语义上高度重合（都是管理记忆库、看用量、管配额），
差别只在「管自己」还是「管这个商户下的所有人」。

### 举一个具体例子

同一个面板，两种身份看到的差异：

| 功能区块 | 个人用户 | 商户管理员 |
|---|---|---|
| 记忆库（卡片增删改查） | 显示 | 显示（管理商户下所有用户的库） |
| 我的订阅（personal/pro/max、支付） | 显示 | **隐藏**（商户不按个人套餐付费） |
| 商户管理（终端用户列表、配额） | **隐藏** | 显示 |
| 商户套餐与账单 | **隐藏** | 显示 |
| MCP / Skills / 备份 等本地能力 | 显示 | 显示 |

### 我们需要你们提供的

要做到「按权限显隐」，我们必须知道**当前这个人的权限是什么**。
请选一种方式给到：

**方式 1：userinfo / id_token 里带 claim（推荐，最简单）**

```json
{
  "sub": "...",
  "email": "boss@acme.com",
  "merchant_id": "mbz_xxx",          // 属于哪个商户；没有则不返回
  "merchant_role": "admin",           // admin | member；没有则不返回
  "merchant_features": ["accounts", "billing", "quota"]   // 可选：细粒度功能开关
}
```

**方式 2：一个权限查询接口**

```
GET /api/v1/merchants/{id}/members/{email}/permissions
→ { "role": "admin", "features": ["accounts", "billing", "quota"] }
```

**方式 3：只告诉我们"是不是商户管理员"，细粒度由我们自己定**

```json
{ "merchant_id": "mbz_xxx", "is_merchant_admin": true }
```
我们按固定规则展开（admin → 全部商户功能；member → 只读）。

### 还需要确认的两点

1. **商户下有哪些终端用户？**
   - 你们的 `/api/v1/accounts/{email}/subscription` 是按邮箱查的
   - 商户维度需要「列出该商户的所有终端用户」—— 有这个接口吗？
   - 如果没有：**商户的终端用户总数怎么统计？**（决定 `caps` 缩放，见问题一第 3 点）

2. **商户管理员能不能代表终端用户查询权益？**
   - 例如商户管理员要看「我的第 37 个用户订阅了什么」，该调哪个接口？
   - 还是说商户管理员根本不该看到单个终端用户的订阅细节（只看聚合）？

### 如果暂时给不了权限模型

我们会降级成：**按本地商户表判定**（该账号在我方注册过商户 → 视为商户管理员），
显示全部商户功能、隐藏个人订阅。这能跑，但：
- 无法区分「商户管理员」与「商户普通成员」
- 无法做细粒度开关
- 商户身份只在我们的库里，你们看不到

## 请求五：商户维度的查询接口

现有接口都是个人维度：

```
GET /api/v1/accounts/{email}/subscription    ← 按邮箱
```

**请提供或确认**：

| 需要的接口 | 用途 |
|---|---|
| `GET /api/v1/merchants/{id}/subscription` | 商户套餐本身的状态 |
| `GET /api/v1/merchants/{id}/accounts` | 该商户下的终端用户列表（分页） |
| `GET /api/v1/merchants/{id}/usage` | 用量统计（可选，用于配额预警） |

如果这些暂时没有，请告诉我们**短期内的替代口径**（比如「商户套餐下发时带 `per_user_caps`，
由我们按本地租户数自己乘」）。

## 我们已实现的部分（供你们对照，不需要动作）

| 能力 | 状态 | 说明 |
|---|---|---|
| 商户注册 | ✅ | 名称 + 域名 → 生成 `mch_`/`msk_`，**密钥只存 sha256** |
| 密钥轮换 / 吊销 | ✅ | 轮换后旧密钥**立即失效**（商户密钥会进对方服务端，必须能立刻作废） |
| 商户实例校验 | ✅ | `POST /cloud/merchant/verify`，凭 `mch_`+`msk_` |
| 按 owner 隔离 | ✅ | 只能操作自己名下的商户，越权 403 |
| 商户套餐订阅 | ⏳ | 走 `subscribe?sku=<MEMORY_MERCHANT_PLAN_SKU>&merchant=<id>` 深链，等正式 sku |
| UI 分 tab | ✅ | 「客户端订阅」/「商户接入」两个独立面板 |
| **按角色显隐** | ⏳ | 商户管理员只看到商户功能 —— **等你们答复问题四才能做** |

## 在我们收到答复前，怎么降级

| 情况 | 我们的处理 |
|---|---|
| 商户 sku 未定 | 用 `sub-merchant` 占位；商户订阅链接可用，但对方可能返回 `unknown_plan` |
| 商户权益路径未定 | 商户状态停在 `pending`，不影响已有个人订阅链路 |
| 商户管理员身份未定 | UI 不区分角色，商户管理员和个人用户看到同样面板（不理想，但不阻塞） |
| 终端用户数未知 | `caps` 按 `seats × 1000` 兜底（同个人套餐口径） |

**以上都不影响现有个人订阅链路**（那条已经跑通并有每日核对兜底）。

---

## 一句总结

个人订阅那条路已经通了。商户这条路上我们缺两样东西，都在你们侧：

1. **一个商户主体的标识** —— 不管是你们签发商户道印灵钥（模型 B）、
   还是承认我们的商户 ID 并把权益按商户下发（模型 A）。没有它，商户套餐会和个人套餐
   混在同一个人的权益里。
2. **一个权限来源** —— 我们要让商户管理员用同一个 admin 面板、按权限显隐功能，
   就必须知道"这个账号在哪个商户、是什么角色"。没有它，只能按本地商户表硬判，
   区分不了管理员与普通成员。

其余（sku、caps 缩放、终端用户统计）都是这两样确定后的自然延伸。
