# 术语对照表（GLOSSARY）

仓库对外的文档与提交信息统一用**修行雅称**表达，技术含义不变：同一件事有「修行说法」和「工程说法」两种写法，
读者按上下文都能对上。目的很单纯——文档是给同一个圈子里的人看的，用词干净一点，仓库更好长期维护。

本表是**唯一真源**：写新文档、写提交信息、写发布说明，都按这张表来。

## 1. 修行三件套（最常用）

| 修行说法 | 工程含义 | 落地形态 |
|---|---|---|
| **参悟天机** | 静态分析：读二进制/字节码/包结构，还原符号与控制流 | 反汇编、反编译、符号恢复、壳与混淆识别 |
| **推演阵法** | 动态推演：跑起来观察数据流与调用时序 | 调试器、Hook、桩与探针、协议重放 |
| **破障解禁** | 防护机制研究：理解限制条件并验证其边界 | 校验逻辑梳理、沙箱/检测项清单、合规评估报告 |

一句话总揽：

> 以参悟、推演、观想、解构入道，借神识扫查、附灵牵线观其运行，寻命门阵眼、破禁制障眼，于试炼斗法中验证护山大阵之效。

对应工程语：观想解构、附灵牵线、结构还原、扫描探测、运行时观测、弱点定位、破障解禁研究、验证与防护评估。

## 3. 执行工具

```bash
# 提交前自检：正文正文（含代码块）里是否还有高危词
node scripts/check-sensitive.mjs

# 批量把文档换成雅称（默认 dry-run，跳过代码块与行内代码）
node scripts/desensitize-docs.mjs
node scripts/desensitize-docs.mjs --yes
```

## 4. 提交信息写法

提交信息按「类型(范围): 做了什么」写，范围用雅称，动词保持工程语义：

```
docs(天机阁): 典籍库接入说明 + 类型标签口径 + 去敏术语表
feat(演武): 参悟结果按类型归档与检索
fix(护山): 大阵自检漏检一处边界
```

三种类型前缀：`feat`（新能力）/ `fix`（修缺陷）/ `docs`（文档）。范围里别出现被替换掉的那批词。

## 5. 边界

- **代码标识符与人机协议不改**：`type:sqli`、`kind:template`、`redteam-kb` 这类 tag 是数据侧标识（已有卡片、检索与导出都依赖），只在**文档叙述**里用雅称，代码与数据保持原样。
- **代码块与行内代码不改**：`-ExecutionPolicy Bypass`、`payload.cards`、Mermaid 节点 `C1-->C2` 是命令与流程图节点，改了直接坏。
- 误伤白名单在脚本里：`C\d\s*(-->|\{)`、`ExecutionPolicy Bypass`、`payload.cards`。
- 单独出现的「扫描」「横向」「演练」不替换——「目录扫描」「横向对比」「灾备演练」都是普通技术表达。
